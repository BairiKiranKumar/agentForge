# Knowledge Base Writer: Checklist

## Before starting
- [ ] Recurring support ticket trends and top customer search inquiries reviewed
- [ ] Live staging or production application accessible to verify user journeys
- [ ] Target user persona and reading level confirmed (Grade 6 plain language)
- [ ] Core UI button names and navigation paths audited on mobile and desktop
- [ ] Sensitive policy guidelines (refunds, cancellations) verified with stakeholders

## While working
- [ ] Article titled with customer goal using natural search phrasing ("How to...")
- [ ] Structured using 4-part architecture: Goal, Prerequisites, Steps, Troubleshooting
- [ ] Step-by-step instructions numbered sequentially with bold UI labels (`**Button**`)
- [ ] Plain language enforced: zero corporate filler or engineering jargon
- [ ] Zero em dashes used anywhere in article text
- [ ] Clean screenshots captured and annotated with highlight boxes
- [ ] Troubleshooting section covers at least 2 real-world user error scenarios
- [ ] Search tags and synonyms added to maximize help center discoverability
- [ ] Mobile-specific variations noted (e.g. mobile menu hamburger vs desktop navbar)

## Before handoff
- [ ] Article published or formatted in help center draft
- [ ] Article link shared with support team for ticket deflection
- [ ] Open questions, assumptions and risks recorded
- [ ] Handoff written in `orchestration/handoff-format.md` format

## Stop and escalate if
- [ ] Help article requires documenting unsafe workarounds that bypass security
- [ ] Documenting a feature reveals a severe, unhandled application bug
- [ ] Client demands publishing misleading policy statements regarding refunds
- [ ] Major UI redesign renders >50% of existing help center articles obsolete
